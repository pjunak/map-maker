# ADR-0001: Use Python 3.14 for the application and terrain engine

**Status:** Accepted
**Date:** 2026-09-01
**Deciders:** Repository owner

## Context

The first Map Maker product is a deterministic terrain generator. It needs array
computation, interpolation, spatial statistics, raster and vector GIS I/O,
coordinate transformations, visual diagnostics, and access to optional
landscape-evolution software. It begins as a local command-line tool and may
later be exposed through a hosted web application.

The repository has no inherited implementation stack. CPython 3.14 is a fixed
project choice. As of this decision, the core numerical and GIS packages needed
for the first stages provide Python 3.14 support. Some optional research-oriented
landscape engines may lag and must not constrain the core runtime.

## Decision

Use CPython 3.14 for project-owned application and terrain-engine code.

- Keep the computational engine independent of CLI and future HTTP frameworks.
- Use compiled scientific and GIS libraries through their Python APIs where
  they satisfy the contract.
- Keep optional engines behind adapters, including engines that require a
  separate environment or external process.
- Consider Rust only for a measured hotspot or a portable WebAssembly kernel;
  do not introduce a second project-owned implementation language speculatively.
- Use TypeScript only when an interactive browser interface is built.

## Options considered

### Python 3.14

| Dimension | Assessment |
|---|---|
| Scientific and GIS ecosystem | Excellent |
| Initial development cost | Low |
| Native custom-code performance | Moderate |
| Local CLI and hosted API | Strong |
| Browser execution | Weak without a service or specialized runtime |

Python provides direct access to the most relevant numerical, GIS, spatial
statistics, and landscape-modeling ecosystem. Expensive operations can execute
inside compiled dependencies while orchestration remains readable and easy to
test.

### Rust

| Dimension | Assessment |
|---|---|
| Scientific and GIS ecosystem | Moderate and developing |
| Initial development cost | High |
| Native custom-code performance | Excellent |
| Local CLI and hosted API | Strong |
| Browser execution | Strong through WebAssembly |

Rust offers excellent performance and distribution properties, but would
require substantially more project-owned numerical and geomorphic code. It
remains a possible implementation for isolated, profiled bottlenecks.

### TypeScript

| Dimension | Assessment |
|---|---|
| Scientific and GIS ecosystem | Limited for this domain |
| Initial development cost | Moderate |
| Native custom-code performance | Moderate |
| Local CLI and hosted API | Strong |
| Browser execution | Excellent |

TypeScript is a good fit for a future interactive editor, but not for the first
authoritative scientific pipeline.

## Consequences

- The first useful terrain prototypes can compose mature scientific and GIS
  libraries instead of reimplementing their algorithms.
- Python and dependency versions must be locked and included in build manifests
  to support deterministic reproduction.
- CPU-heavy Python loops must be avoided or profiled before optimization.
- Python 3.14 compatibility must be verified before adopting each compiled
  dependency.
- Optional landscape engines that do not support 3.14 will run through an
  isolated adapter or wait until they become compatible.
- A future web product will have at least a backend/frontend language boundary.

## Follow-up

1. Define the terrain project, constraint, profile, and build-manifest schemas.
2. Select the smallest Python 3.14-compatible dependency set for the first
   interpolation spike.
3. Benchmark deterministic generation before considering native extensions.
